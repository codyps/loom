# Litmus tests against a reference memory model

`reference.txt` holds small concurrent programs and, for each, the outcomes the
RC11 memory model allows, as computed by the [herd7] simulator. The test in
`tests/litmus_reference.rs` runs every program under loom and checks that loom
finds no outcome that is not allowed, and all the allowed ones except those
recorded as known gaps. `mod.rs` documents the program notation and contains
the interpreter that runs a program under loom.

The reference model is herd's `rc11.cat` ("Repairing Sequential Consistency in
C/C++11", Lahav et al., PLDI 2017) with one change: release sequences are the
C++20 ones, which is what Rust has. In `rc11.cat` that is the single line

    let rs = [W & (RLX | REL | ACQ_REL | ACQ | SC)]; (rf; myrmw)*

instead of the C++11 definition, in which a later store by the same thread
continues a release sequence.

## Known gaps

Loom executes one operation at a time and only lets an operation observe what
has already been executed. Two consequences show up as missing outcomes:

- A read-modify-write always goes last in the modification order of the
  stores executed so far. It cannot be placed before a store that was
  executed earlier but that nothing orders before it.
- The order in which `SeqCst` operations are executed is used as their total
  order. An outcome that needs a `SeqCst` order that no possible execution
  order agrees with is not found. This takes a relaxed load (or a
  read-modify-write, per the previous point) that forces two `SeqCst`
  operations to execute in one order, without ordering them in the memory
  model.

Neither makes loom report a failure that cannot happen. Both mean that loom
can miss a bug that only shows up in such an execution.

## Regenerating

This needs `herd7` (herdtools7; build `herd/herd.exe` with dune) and its
`libdir`, with the modified model saved there as `rc11_cxx20.cat`.

1. `python3 tools/gen.py` writes the programs to `programs.txt` (one per
   line), an index to `index.txt`, and a C litmus file per program to `lit/`.
2. Run herd on each: `herd7 -I <libdir> -model rc11_cxx20.cat lit/<name>.litmus
   > hout/<name>.txt`.
3. Run loom on the programs with the `litmus_gen` test:
   `LOOM_LITMUS_IN=programs.txt LOOM_LITMUS_OUT=lout/p00 LOOM_LITMUS_BUDGET=5
   cargo test --release --test litmus_gen`. The larger programs do not finish
   within the budget; those are only checked for outcomes that are not
   allowed. Split the input over several files and processes to use more
   cores.
4. `python3 tools/compare.py lout` prints the totals, and writes the programs
   for which loom found a forbidden outcome to `lout/extra.txt` and those for
   which it missed one to `lout/missing.txt`.

The full set generated by `gen.py` is about 18,000 programs: every program of
two threads with two operations each over two variables, using relaxed and
`SeqCst` loads, stores and exchanges and `SeqCst` fences, plus random samples
of larger shapes (up to four threads, three variables, acquire / release).
`reference.txt` is the subset that loom explores quickly.

[herd7]: https://github.com/herd/herdtools7
